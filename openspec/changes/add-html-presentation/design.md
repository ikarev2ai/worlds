# Design

## Context

См. `proposal.md` — Why и спецификации `static-content-publishing` и `content-exploration`. Репозиторий содержит только Markdown-источники и отдельный PDF-экспортёр на Python 3 с PyMuPDF. Его упрощённый Markdown-конвертер не поддерживает таблицы и ссылки и связан с PDF, поэтому повторно использовать его для сайта нельзя. Веб-инфраструктуры, package manifest и тестового набора сейчас нет.

## Goals / Non-Goals

**Goals:**

- Одна команда создаёт полный сайт в `dist/html/` без ручной регистрации новых миров и произведений.
- Исходный код сайта отделён от контента и PDF-инструмента.
- Сайт работает на любом статическом HTTP-сервере, включая размещение в подкаталоге.
- Ошибки источников и ссылок обнаруживаются до замены последнего успешного результата.

**Non-Goals:**

- Не вводить CMS, backend, аккаунты, комментарии, редактирование и аналитику.
- Не публиковать OpenSpec, шаблоны миров и служебные инструкции как примеры UWI.
- Не настраивать другие хостинги и не изменять автоматически настройки репозитория; включение GitHub Pages остаётся действием владельца.
- Не создавать отдельный frontend-фреймворк или переносить содержимое в данные сайта.

## Decisions

### 1. Отдельный генератор на Python 3

Разместить реализацию в `web/`: `build.py`, HTML-шаблоны в `templates/`, статические ресурсы в `assets/`, точно зафиксированные зависимости в `requirements.txt`. Команда: `python3 web/build.py`; зависимости устанавливаются из `web/requirements.txt`.

Использовать `markdown-it-py` с отключённым raw HTML, `mdit-py-plugins` для якорей и `Jinja2` с autoescape. Эти зависимости добавляются явно; Node.js и frontend-зависимости не нужны.

Альтернативы: VitePress или MkDocs дали бы готовые функции, но потребовали бы адаптации каталогов и приняли бы лишнюю конфигурацию и зависимости. Рендеринг Markdown в браузере нарушил бы чтение без JavaScript. Изменение PDF-конвертера связало бы два независимых представления.

### 2. Каталог источников как модель сайта

Сканировать фиксированные корни и исключать `template.md`, `template-work.md`. Тип документа и связи определять путём, а не вручную составленным списком:

- `README.md` → `/`;
- `ontology/manifest.md` → `/ontology/`;
- `ontology/questions.md` → `/ontology/questions/`;
- `worlds/README.md` → `/worlds/`;
- `worlds/<slug>/README.md` → `/worlds/<slug>/`;
- `worlds/<slug>/works/<work>.md` → `/worlds/<slug>/works/<work>/`.

Каждый маршрут записывается как `<route>/index.html`. Заголовок страницы берётся из первого H1; родительские связи произведений — из путей. Версия на стартовой странице остаётся в исходном `README.md`, без отдельной копии. Для `worlds_index` исходный HTML не выводится: шаблон показывает только сгенерированный список миров с единственным H1 «Каталог всех миров» и предупреждение «Внимание: описания миров и произведений содержат спойлеры». Для карточек вычисляется короткое название как часть H1 до первого ` — `; полный заголовок сохраняется на странице мира, в хлебных крошках и поисковом индексе.

Для `questions` вступительные абзацы реестра не выводятся: перед рендерингом генератор оставляет заголовки и блоки вопросов (H3 внутри раздела или жирный абзац «Вопрос N.»), отбрасывая остальные абзацы верхнего уровня. Число вопросов в источнике и в готовой странице сверяется, расхождение — ошибка сборки. Исходный `document.text` и его SHA-256 не меняются.

Для `home` шаблон выводит русское название проекта (константа генератора, она же попадает в заголовок вкладки и поисковый индекс) и первый абзац исходного `README.md` с кратким описанием; его вводная фраза «Название: » опускается, потому что название уже выведено заголовком; остальные его разделы заменены карточками переходов к онтологии, вопросам и мирам, поэтому строка версии и прочие разделы не попадают и в поисковый индекс.

### 3. Двухпроходное преобразование

Первый проход читает все документы, строит реестр источник → маршрут и собирает заголовки с Unicode-aware GitHub-совместимыми якорями, включая устранение дублей. Второй преобразует Markdown, перезаписывает ссылки и создаёт страницы.

Ссылки на опубликованные `.md` преобразуются в относительные URL с якорями. Ссылки на существующие, но непубликуемые файлы проекта ведут на исходный файл через настраиваемый `repository_url`; внешние URL не изменяются. Отсутствующая локальная цель или якорь является ошибкой сборки. Относительные URL позволяют размещать сайт в подкаталоге.

Raw HTML экранируется, динамические строки вставляются в шаблоны с autoescape. Кириллица в контурах не нормализуется и не транслитерируется; якоря генерируются только для навигации.

Перед Markdown-рендерингом таблица произведений мира преобразуется только в presentation-текст: первая и пятая исходные колонки сохраняются, а название связывается с `.md`-путём соответствующего произведения и затем преобразуется общим link resolver. Число строк сверяется с найденными произведениями. Исходный `document.text` и его SHA-256 остаются неизменными. Дополнительный шаблонный блок «Произведения мира» удалён как дублирующий табличные ссылки.

Для открытых вопросов структура нормализуется непосредственно в `ontology/questions.md`: исходная метка «Естественный язык» и жирный префикс вопроса заменяются H3 с полным названием, после которого отдельно сохраняются метка естественного языка с исходным текстом и контур UWI. Отдельное presentation-перестроение не требуется. Меняются только разметка и порядок блоков; закрытые вопросы, формулировки и версия не затрагиваются.

Отсылки мира к вопросам реестра записываются в исходном Markdown как явные ссылки вида `[Вопросу 8 «Предзнание без петли времени»](../../ontology/questions.md#якорь)` с названием раздела вместо номера и без имени файла. Общий link resolver превращает их в ссылки на страницу вопросов с якорем и проверяет якорь при сборке. Якоря кириллические и совпадают с алгоритмом GitHub, поэтому ссылки работают и в исходниках. Повторная отсылка того же абзаца содержит только номер вопроса со ссылкой. Формат задан в `worlds/template.md`.

### 4. Локальный поиск как производный индекс

При сборке создавать детерминированный `search-index.json`: тип, заголовок, URL, родитель и текст без Markdown-разметки. Небольшой JavaScript загружает индекс при первом запросе, нормализует регистр и `ё/е`, ранжирует совпадения в заголовке выше совпадений в тексте и формирует snippet. Результаты добавляются через DOM без интерполяции HTML.

Навигация и контент присутствуют в HTML сразу. Поиск — progressive enhancement; без JavaScript остаются все страницы и обычные ссылки. Внешние шрифты, библиотеки и CDN не используются.

### 5. Адаптивное представление и доступность

Один `base.html` задаёт landmark-структуру, общую навигацию и skip-link. `site-header` закрепляется через `position: sticky` с z-index ниже skip-link; `scroll-padding-top` учитывает высоту шапки на desktop и mobile. Системные шрифты и CSS обеспечивают читаемую ширину текста, видимый focus, достаточный контраст и адаптивное меню. Футер на всех страницах содержит имя автора «Ivan Karev» как ссылку `mailto:` на `ikarev2ai@gmail.com`; адрес не показывается, текст задан в `base.html`. Для широких таблиц и `pre` используются собственные контейнеры прокрутки с keyboard focus; основная страница не прокручивается горизонтально. Общие переменные `--code-bg` и `--code-ink` задают тёмный фон и светлый текст для inline `code` и `pre`, обеспечивая контраст не ниже 4.5:1.

Подпись проекта в шапке не переносится (`white-space: nowrap`); на mobile при нехватке ширины она целиком переходит под название UWI за счёт `flex-wrap: wrap` у `.brand`.

Корневые Markdown миров нормализуются одним презентационным проходом: inline-контур после «Контур UWI» заменяется fenced-блоком, а разделитель `; ` переносит следующую формулу на новую строку. Символы формул вне разделителей не меняются; существующие fenced-блоки и карточки произведений не переписываются.

### 6. Проверки и атомарная публикация сборки

Генератор проверяет обязательные файлы, уникальность маршрутов, соответствие всех найденных миров и произведений страницам, связи мир ↔ произведения, внутренние цели и якоря. Он также формирует `build-manifest.json` с упорядоченным списком источников, маршрутов и SHA-256 содержимого; временные метки не записываются.

Сборка выполняется во временный соседний каталог внутри `dist/`. Только после всех проверок прежний `dist/html/` переименовывается в резервный, новый каталог становится `dist/html/`, после чего резерв удаляется. При ошибке новый результат удаляется, прежний остаётся или восстанавливается. Повторная сборка не сохраняет страницы удалённых источников.

Поскольку в проекте нет тестового набора, новый test framework не вводится. Обязательные проверки являются частью обычной сборки; приёмка дополняется реальным запуском статического сервера, HTTP-обходом сгенерированных маршрутов и ручными browser-сценариями из спецификаций.

### 7. GitHub Pages через официальный Actions pipeline

Добавить `.github/workflows/html-pages.yml` с триггерами `push` по `main` и `workflow_dispatch`. Job собирает сайт той же командой `python3 web/build.py` после установки `web/requirements.txt`, создаёт `dist/html/.nojekyll`, затем вызывает `actions/configure-pages`, `actions/upload-pages-artifact` и `actions/deploy-pages`. Версии actions фиксируются мажорными тегами; workflow получает только необходимые `pages: write`, `id-token: write`, `contents: read` и отменяет устаревшие параллельные запуски без отмены уже выполняемого deploy.

Относительные URL, включая путь до `search-index.json`, не зависят от имени репозитория, поэтому один artifact работает и локально, и в `/<repository>/`. Workflow не коммитит `dist/` и не меняет настройки репозитория: для первого запуска владельцу нужно выбрать GitHub Actions как Source в Settings → Pages.

### 8. Отсылка к реестру в манифесте и PDF-экспорт

По указанию автора (2026-11-27) отсылка к реестру в разделе 5 `ontology/manifest.md` записывается Markdown-ссылкой `[реестре вопросов](questions.md)` вместо имени файла; общий link resolver превращает её в ссылку на страницу вопросов. Это единственная правка манифеста в изменении: автор решил не поднимать версию, правка ожидает следующего выпуска. Экспорт в PDF не обрабатывает ссылки, поэтому `scripts/export_pdf.py` выводит Markdown-ссылку её текстом без адреса; иначе в PDF появилась бы сырая разметка.

## Risks / Trade-offs

- [Нестандартный Markdown в отдельных документах] → Поддерживать наблюдаемые конструкции через CommonMark, tables и fenced code; остальные случаи выявлять проверкой всего текущего корпуса, не переписывая источники.
- [Расхождение якорей с привычными GitHub-ссылками] → Использовать один Unicode-aware алгоритм для генерации и разрешения якорей и проверять существующие fragments при сборке.
- [Рост поискового индекса вместе с корпусом] → Загружать JSON лениво и хранить только необходимые поля; при текущем объёме отдельный search engine не нужен.
- [Собственный генератор требует сопровождения] → Ограничить его одним узким pipeline и явными проверками вместо создания универсального static site framework.
- [Ссылки на непубликуемые файлы требуют внешнего репозитория при открытии] → Сохранять их как исходные справочные ссылки; основные страницы, навигация и поиск остаются автономными.

## Migration Plan

1. Зафиксировать зависимости и добавить `web/`; в Markdown миров менять только многострочное оформление контуров, а PDF-экспорт не менять.
2. Выполнить сборку во временный каталог и проверить полный текущий корпус и все сценарии.
3. Опубликовать результат только как `dist/html/`; сгенерированные файлы не коммитить.
4. Для отката удалить `web/` и новый `dist/html/`; прежние источники и PDF-экспорт продолжат работать без миграции.
